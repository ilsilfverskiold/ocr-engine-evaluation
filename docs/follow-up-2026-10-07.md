  Check other embedded headings and whether block allocation can also hide
  present text from the diagnostic.
- Preserve structural requirements and one-to-one credit. Finding a phrase
  inside a paragraph must not award heading credit or allow a block to earn
  credit repeatedly.

  Verify rather than assume the aggregate impact on other items.

`table_header` item `Description | Qty | Price | Amount` receives `wrong_type`
despite full-content similarity 1.000. The returned Markdown is valid:

```markdown
| Description | Qty | Price | Amount |
|---|---|---|---|
| 000000111 | 1 | 193.00 | 193.00 SR |
```

The Markdown library correctly renders the first row as `<thead>` with `<th>`
cells. Our `markdown_structure.blocks()` then emits **every** `<tr>` as
`table_row`, discarding whether it is a header. The catalogue generator allows
`table_header`, but the output parser cannot produce that type. The matcher
compares the type names directly and incorrectly rejects this exact match.

Current saved report scope: **146 table-header verdicts across 10 pages and
10 engines: 129 wrong_type, 17 absent, zero correct**. This does not prove all
146 outputs contain valid headers; it proves the current implementation cannot
credit this catalogue type even when the header is valid. Unlike the embedded
heading diagnosis above, this defect can directly lower the headline score.

Required correction and verification:

- Preserve table-header semantics from actual Markdown/HTML output. Do not
  relabel every table row as a header or accept a data row as a header merely
  because its words match.
- Define the compatibility rule for older generic `table_row` reference items
  and for header/data rows, including HTML row headers and merged cells.
- Audit all allowed catalogue types against parser output and matching rules;
  a reference type must not be impossible to satisfy by construction.
- Add regression coverage for Markdown headers, HTML headers, ordinary data
  rows, mixed row-header cells and wrong-format text with identical words.
- Rescore affected Markdown outputs from saved calls, inspect before/after
  verdicts and update the report. No new OCR or judge calls are needed.

## 1c. Receipt audit: segmentation, key/value tables and literal text

**Status: Sonnet sroie_000 audited against its saved answer, parsed blocks,
verdicts and source image; corrected in the v2 replay above.**

The headline is `(1 correct + 0.5 × 3 partial) / 27 = 0.0926`. The other
23 items get zero: 13 wrong_type and ten absent. The arithmetic is correct;
the verdicts are not a reliable assessment of this output.

### False absence and overly coarse matching

All ten items called absent have their text in the output. Nine are exact
contained phrases after normalizing case/whitespace. The tenth is the literal
asterisk-decorated thank-you line, mishandled by reference parsing below.

- COPY, company name, ROC number, address, phone/fax and email are in one
  rendered paragraph (block 2). The matcher assigns it only to the address,
  with 0.529 similarity, and calls the other five items absent. Whole-block
  similarity and indivisible block allocation conflate text presence with
  different paragraph segmentation.
- `Qty: 1` is present in the same returned row as Total Exclude GST (block 15).
- VISA CARD, the card suffix and Approval Code are together in paragraph 20.
  Comparing each short reference with the entire paragraph misses them.
- The return-policy sentence and thank-you message share paragraph 21. The
  return-policy item consumes the block; the second item cannot be matched.

One-to-one *content ownership* is needed to prevent duplicate credit, but
whole-block exclusivity alone is too coarse for several distinct reference
items contained in one block. Define how segmentation is assessed separately
from presence. Support disjoint spans without crediting the same words twice;
do not claim a missing transcription merely because the paragraph is longer.

Additional reproduction: Sonnet `invoice_002` returns seller `Tax Id:
959-84-2124` and `IBAN: GB20BAKH22085364527355` together in paragraph block 5.
Whole-block similarity is 0.567164 for the Tax ID and 0.736842 for the IBAN.
Both exceed the 0.5 candidate threshold, but the greedy matcher chooses the
IBAN and consumes the entire paragraph. The Tax ID then receives `absent`.
The IBAN receives only `partial` despite its complete label/value being present.
The client Tax ID is credited because it occupies a separate paragraph.
This was a confirmed scoring defect, not a missing OCR value. It is now
covered by a regression and rescored with disjoint spans; unrestricted reuse
of the same content is still prohibited.

### Valid label/value tables rejected

Eleven key_value items are labeled wrong_type solely because they are emitted
as table rows: Invoice No, Date, Cashier, Sales Person, Bill To, Address and five
total/amount rows. The matching code accepts key_value only as a paragraph.

`key_value` is a semantic reference category, not a Markdown block type. A
valid two-column Markdown table can preserve a label/value relationship.
This compatibility policy must assess that association rather than reject the
whole representation. It must not accept arbitrary unrelated cells or confuse
an item table with a field table. The known table_header mismatch is an
additional, separate defect on this page.

### Literal reference text interpreted as Markdown

The newer catalogue asks for plain visible text, but `_reference_text()` runs
it through a Markdown renderer. For this page, printed
`****Thank You. Please Come Again.****` becomes
`*thank you. please come again. *`, while Sonnet correctly escapes the printed
asterisks. Reference interpretation alters the expected text. Preserve literal
source text and define handling for older catalogues that contain markup;
add tests for literal asterisks and other Markdown-significant characters.

### Actual output losses and correctly unavailable metrics

- `TAX INVOICE` is emitted as bold emphasis, not a heading: wrong_type is
  justified under the agreed heading-syntax rule.
- `KINGS SAFETY SHOES KWD 805` is outside the returned item table. The text is
  present, but its association with the item row is not preserved in the table.
  A table-row structure penalty is justified; do not turn it into missing text.
- Block precision/recall/F1 and reading order are N/A because there is no full
  Markdown reference for this receipt. Its sampled image-authored catalogue
  establishes checklist coverage, not a complete set of document blocks.
  Explain this in the report. Any future sampled-item order metric must be
  labeled separately; do not fabricate a full reference or another judge run.
- CER 0.0273 and WER 0.0804 use the independent plain-text reference and measure
  textual differences. Their low values do not prove correct structure, but
  they are consistent with the many false missing-text diagnostics above.

The parser/matcher contract needs a coordinated correction across reference
types, content spans and valid output representations before republishing
