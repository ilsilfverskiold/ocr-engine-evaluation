# KV and missing-text audit — 2026-10-09

Status: audit complete; two shared KV defects repaired and judged-text reporting restored. Remaining scorer/policy gaps are explicitly listed below. No inference or judge API calls authorized or made in this audit. Source baseline: `20261007T121019Z`.

## What was actually wrong

The earlier native-row fix is shared scorer code, not a document whitelist, but it only resolves **printed row identity + column header**. It cannot solve every split identifier, blank, checkbox or combined-field case. This audit covers all five tax pages and all four KV engines (20 results), their returned pairs, saved verdicts and failed model-approval validations. All five source images were inspected. Accepted gold references have not been edited.

Two general defects were corrected:

1. **Split identifiers were treated as amounts.** The numeric guard rejected `645`, `83`, `9823` as candidates for the SSN `645 83 9823`, although the saved judge explicitly approved those three cells. Identifier components now retain digit groups and leading zeros; their complete order must agree. Wrong amounts such as `1000` for `100` and `1234` for `12.34` remain wrong. Matching fragments only proposes a review; it never automatically establishes field identity.
2. **Native unchecked boxes disappeared in table conversion.** Every tax page has actual `NOT_SELECTED` provider blocks inside cells. HTML previously rendered these as empty strings. The adapter now retains physical cell selection metadata alongside unchanged table HTML. KV can interpret that proven state as false; an ordinary empty cell still cannot become false. Existing rejected approvals are replayed only after verifying the original pair list, original model-selected IDs, complete value coverage and exclusive output ownership. Original paid requests/replies remain unchanged. Future live runs and offline rescoring use the same code.

## Blank values: decision still separate from defect repair

An empty **reference** has no distinctive value to support value-assisted key matching. A key or native context can still establish its identity, so blank detection is measurable, but including these fields in the headline makes engines' different conventions disproportionately important. Tax references have 21–34 blanks per page.

Recommendation: populated-reference accuracy as KV headline, with blank-field accuracy and invented values reported separately. `false` and numeric zero are populated values. An empty **engine answer for a populated reference** must continue to fail. Schema has a supplied key contract and need not adopt the same blank policy.

Pending the user's policy choice, keep the existing headline and add `kv_populated_accuracy`, `kv_populated_total`, and `kv_blank_accuracy` consistently to the evaluator and reports. This does not silently change the agreed denominator.

## Remaining tax failures: do not call these all recognition errors

- **Combined values are still allocated as whole output IDs.** Once an output containing several different fields supplies one reference, it cannot supply another. Tax year begin/end components, the combined Dependents form value, and the sidebar's three standard-deduction amounts expose this. A future fix must reserve non-overlapping content spans, with confirmed field/owner context; it must not reuse the same number arbitrarily for different fields. The judge prompt also currently prohibits output-ID reuse, so previously rejected/no-selection replies cannot be rewritten as approvals.
- **Multi-cell blanks:** the validator requires one matched empty output for a blank reference and rejects several empty SSN cells as incomplete coverage. This is separate from unchecked boxes. Blank headline policy may remove this from the main score, but the diagnostic still needs explicit ownership rules.
- **Selection status in a FORMS key:** Textract sometimes puts `NOT_SELECTED` in the key alongside the line-7 label while the value is the capital-gain amount. Treating that amount as the checkbox value fails. Keep separate semantic components and native provenance; do not globally equate empty with false.
- **Categorical selections versus Boolean references:** Gemini and Qwen often return `Filing Status: Single` or `Digital Assets: Yes`; the reference uses separately named Boolean options. A value-only candidate search for `true` will not find `Single`. The scorer needs a field-context-aware representation rule. Absence of an unselected option is not automatically evidence that it was read correctly.
- **Printed context lost:** duplicated `Last name` keys and multirow dependent headers can be ambiguous after flattening. The earlier payslip matcher requires a printed owner string; `Dependent 1` is reference context, not that table's printed row key.
- **Reference scope remains debatable:** `Footer form`, each standard-deduction instruction amount, and explicit empty dependent rows increase the contract beyond a typical filled-form extractor. These are visible page contents, but that does not prove every invented contextual reference key is a printed KV label. Do not quietly delete gold or score them against arbitrary identical values.

Concrete engine-side problems also exist. `tax_000` is supplied upside down. Qwen's KV answer stops at its length limit; Sonnet invents a spouse surname and leaves dependent surname values empty. Gemini omits populated dependent entries on that page. Qwen `tax_003` shifts line labels (its “1c Medicaid…” corresponds to printed line 1d). These cannot all be repaired by synonyms. Other tax calls from the general models record normal stop/end-turn reasons; do not explain their omissions as cap failures without evidence.
