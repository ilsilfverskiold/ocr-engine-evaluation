## 4. Keep text scoring and report evidence clear

The user explicitly wants **CER and WER included in text evaluation now**.
Both already exist in saved text results and the per-page viewer. Make them
visible alongside coverage in engine-level comparisons as well.

| Measure | Plain-language meaning | Direction |
|---|---|---|
| Coverage | How many distinct reference words were found anywhere | Higher is better |
| CER | How much the letters, digits and other characters differ from the reference | Lower is better; zero is a normalized match |
| WER | How much the sequence of whole words differs from the reference | Lower is better; zero is a normalized match |

CER/WER count missing, extra and substituted characters/words. Correct text
in a different order also increases them. They do not directly tell us the
percentage of characters/words visually misread. Our normalization strips
Markdown/HTML, decodes entities, collapses whitespace and lowercases text;
these rates therefore do not measure heading syntax or spacing-entity bloat.
Incomplete/incorrect GT also affects them. Error rates can exceed 100% when
there are many extra characters/words; do not clamp or call 100 minus the
rate a bounded accuracy percentage.

Actual saved Sonnet examples: invoice_000 has coverage 100%, CER 26.36% and
WER 28.74%; bank_001 has coverage 99.65%, CER 0.37% and WER 2.75%. The invoice's
interleaved seller/client ordering contributes to the difference despite
complete distinct-token coverage.

**Recommendation, not an agreed scoring-policy change:** do not average CER
and WER into a single score. They count overlapping errors at different scales;
one wrong digit can be one character error but an entire word error. A blend
adds arbitrary weights and still cannot distinguish recognition from order
or reference defects. Present a compact `Coverage | CER ↓ | WER ↓` comparison.
If a single default sort is needed, choose and label one measure explicitly
rather than inventing a combined accuracy score; keep the other columns visible.

## Latest discussion: structure plus text fidelity in Markdown

The user now explicitly requests a pilot that checks Markdown structure AND
CER/WER of its text. This supersedes the earlier restriction to text-only
CER/WER displays. These remain separate dimensions, not a blended score.

Standards and benchmark practice:

- [CommonMark](https://spec.commonmark.org/0.31.2/) distinguishes heading blocks
  from inline strong emphasis. Valid Markdown can be all paragraphs; merely
  parsing without errors does not prove the required document structure.
- [GFM](https://github.github.com/gfm/#tables-extension-) specifies pipe tables;
  supported HTML headings/tables should also retain their real semantic type.
- [OmniDocBench](https://github.com/opendatalab/OmniDocBench) separates text
  edit-distance evaluation, table structure (TEDS) and reading order. This is
  precedent for separate dimensions, not a claim that its exact method is ours.

Method and limits:

Use Python-Markdown with `tables` and `fenced_code`, then inspect the HTML tree
with BeautifulSoup. Match sampled reference heading text to actual h1–h6 tags
one-to-one, ignoring case, whitespace and a trailing colon. Heading depth is
not scored. The existing model-authored checklist is reused, not newly verified
against every source. Table/list inventory is not a claim that every cell or
list value is correct. This is a focused heading/text pilot, not a complete
replacement structural evaluator or a full CommonMark conformance test.

CER/WER use the existing normalized plain-text reference and normalization:
strip markup, decode entities, lowercase and collapse whitespace. They include
reading-order and reference defects; they do not score heading syntax.
For a future full evaluator, matched-block text errors can separate recognition
from page order, but missing/extra blocks must still count rather than disappear.
